What we are building

The existing system answers questions about DeFi protocols using hybrid retrieval, reranking, deterministic guardrails and live on-chain data. It works, and it is measured. The rebuild does not replace it — it adds a second mode above it, for questions a lookup cannot answer.

Simple question → guard → route → retrieve → grade → generate → verify → answer (unchanged) Investigation → guard → route → plan → ┬ research agent ┐ ├ blockchain agent ┤→ risk → verify → report └ security agent ┘

The governing idea is that the system should stop producing answers and start producing evidence-backed conclusions — things that can be traced to a source, contradicted, or marked as unknown.

Three rules everything else follows from

  • Deterministic where possible. Identifiers, confidence arithmetic, statistics, source reliability and severity thresholds are computed by code. The model interprets, plans and explains — it does not calculate, and it does not rate its own sources.
  • Silence is never safety. "We checked and found nothing" and "we never checked" must never render the same way. This single rule shapes the severity bands, the verification statuses, the stub agents and the report.
  • Keep the simple path simple. An ordinary support question must not get slower, costlier, or more elaborate because an investigation mode exists.
Working constraint Everything so far is built and tested with zero API spend. All 875 tests run offline in 4.2 seconds. Where a step genuinely needs a model, the model call is injected so the surrounding pipeline is still exercised for free.

Foundation

A0

Index hygiene

Shipped

Why it came first

A note in the project memory said some retrieved documents were missing their protocol tag. That turned out to be a symptom of something much larger, and it had to be fixed before any agent could cite evidence — provenance is worthless if the index is not what the code thinks it is.

The defect

write_index called Chroma.from_documents against a persistent directory. That upserts by id: it overwrites ids that still exist and never deletes ids that don't. Every rebuild since the multi-protocol migration layered on top of the last.

What was in the vector storeRowsConsequence
Live chunks (correct)1,091—
Orphans with no protocol tag661Answered unfiltered queries — the generic questions the router declines to scope
Orphans still tagged496Leaked into filtered queries
Total held2,248Dense search read this; BM25 read a clean mirror of 1,091
The worst of it Among the tagged orphans, onboarding/how-to-use-the-hyperevm was indexed under both hyperliquid and hyperevm. That is precisely the cross-protocol leak the protocol filter exists to prevent — reintroduced underneath it by the writer.

Fix

  • write_index now drops the collection before writing.
  • index_drift() reconciles the two stores by doc_id using pure set logic — deliberately metadata-blind, so it catches untagged rows no metadata sweep could reach.
  • build_index --verify checks; --repair re-embeds the corpus mirror locally — no crawl, no network, no cost.

A1

Evidence & claims

Shipped

The vocabulary every agent writes in: Evidence, Claim, EvidenceLink, and the confidence model. Everything downstream depends on these being right, so they were built first and tested hardest — 62 tests.

Three decisions, each pinned by tests

  • Identity is content, not authorship. Every id is a hash of the semantically identifying fields, so the same fact found by two agents is one node. Otherwise running more agents would inflate the independent-source count that confidence is built on. Re-reading an unchanged fact tomorrow does not mint a second observation; reading a metric at a different block does.
  • Stance lives on the edge, not the evidence. A TVL drop supports "activity declined" and contradicts "the protocol is growing". Evidence has no intrinsic polarity — only a relationship to a specific claim does.
  • Source reliability is assigned by rule. PRIMARY / OFFICIAL / COMMUNITY / UNVERIFIED is decided by where something came from. A model asked to rate its own sources rates them well, and confidence built on that is circular.
I shipped the confidence model wrong — the tests caught it

The spec gives confidence as a product of five factors. Implemented directly that collapses (0.95 = 0.59), so I used a geometric mean to fix the deflation.

But a geometric mean is compensatory. With five factors, a term of 0.05 cannot pull the result below 0.051/5 ≈ 0.55 — so a claim the verification stage had actively refuted still reported as moderately confident, and outscored an honest "insufficient evidence". A verification stage that strong evidence can outvote is not a verification stage.

Fix: verification became a gate, not a fifth factor. score = geomean(4 evidence factors) × verification_weight, with CONTRADICTED = 0.0. A refuted claim is not a weak yes; it belongs in the same category as one with no support at all.

Other deterministic choices

  • Reliability takes the best source, not the average. Averaging would mean citing a corroborating forum post alongside the protocol's own docs lowers confidence — penalising thoroughness and pushing agents to cite less.
  • Quality counts distinct source URIs. Otherwise an agent that chunks a document finely looks better-evidenced than one that doesn't.
  • Freshness decays per evidence kind. Market data has a 6-hour half-life; documentation has a year. One global window would either treat live metrics as durable or discard docs that never expired.

Verified against the spec's own worked examples

ClaimSpecOursBand
"Protocol X experienced abnormal withdrawals" — 4 sources, verified0.940.962high
"The withdrawals were caused by an exploit" — 1 source, 2 contradictions0.310.124very low

Same ordering, ours more conservative — the safe direction.

A2

Statistical risk engine

Shipped

Pure standard-library statistics — no ML, no model, no network. The spec calls this the genuinely differentiating piece, and the reason to start with statistics is not simplicity: a z-score can be printed in a report and argued with. An Isolation Forest score cannot.

Four decisions where the textbook version is wrong here

  • The baseline excludes the point being tested. An outlier included in its own baseline inflates the standard deviation — so the bigger the anomaly, the better it hides. This is the most common way a z-score detector silently fails to fire on the event it was built for.
  • Robust scores run alongside classical ones. Mean and σ are themselves destroyed by outliers. On a contaminated window the classical score reads |z| < 3 (blinded) while the median/MAD score reads |z| > 10 (still firing). Severity takes the worse of the two.
  • Undefined returns undefined. A constant series has σ = 0 and no z-score exists. Returning inf, or 0, or dividing by an epsilon manufactures a finding out of a division.
  • Short histories are refused. Below 8 observations there is no baseline, and the honest output is "we have not been watching long enough" — the statistical form of insufficient evidence.
Measured — and it changed the threshold

Benchmarked on 400 days of labelled synthetic data. At the 2σ anomaly bar the spec implies:

precision 0.46 · recall 1.00 · FPR 0.062

Every one of the 21 false positives was an ordinary ~2σ day. A 2σ bar fires on roughly one day in twenty per metric — across a dozen tracked metrics that alerts most days on nothing at all.

Moving anomaly to 3σ (keeping notable at 2σ) gave precision 1.00 · recall 1.00 · F1 1.00 · FPR 0.00 with no recall lost. The spec supports this: its own report table lists "Elevated" and "High Anomaly" as distinct rows.

Stated limitation That benchmark is synthetic. There is no labelled on-chain incident set yet, so the thresholds are uncalibrated and the code says so wherever severity is shown. When real labelled incidents exist, they replace the generator.

Orchestration

B1

Query classification

Shipped

Six categories — cx, research, blockchain_analysis, security_analysis, risk_assessment, full_investigation — added as a third axis on the existing router's output, not a separate classifier node.

Why not its own node The grade stage already eats 43% of a turn's cost. A second classification call would charge every question, including the ordinary ones whose answer is "no investigation needed". All three axes come from one reading of one sentence, so splitting them buys latency, not independence.

The safety clamp

Depth is a separate axis from safety, and safety wins. account_action and out_of_scope collapse any depth back to cx.

This is code, not a prompt instruction. "Investigate whether my drained wallet was an exploit" reads as a full investigation and is an account action — and the account action must win. A prompt instruction is exactly the thing a crafted question argues its way around; this one cannot be argued with.

Three defects surfaced while testing

  • The enum broke checkpointing. Putting a QueryType in graph state produced "deserializing unregistered type — will be blocked in a future version". A str-subclassing enum still counts as an unregistered class. It works today and breaks persisted conversations on a future LangGraph — the same failure class as the metrics object that bit this project before. State now carries the bare value.
  • Guardrail hits on turn 2+ logged the wrong question. Pre-existing. The guard replies before its own state update applies, so under a checkpointer it read the previous turn's question — corrupting the transcript of exactly the safety-critical turns anyone would later audit.
  • The compromise guardrail's copy never reached a user. Pre-existing, and the significant one. The guard writes its reply, then routes to escalate, which replied again — overwriting the carefully-worded compromise warning with generic text and logging the turn twice. Every unit test on that copy passed while it was being discarded end-to-end.
Unmeasured risk Intent accuracy is 87%. Adding a third axis to the same call could dilute it, and that cannot be checked offline. Worth a --routing run (~$1.70) at some point to confirm intent held.
B2

Intelligence Manager & investigation branch

Shipped

The branch exists and runs end-to-end. Agents fan out in parallel — the conditional edge returns a list, which is how the orchestrator schedules genuine concurrent branches rather than a sequence.

Planning is deterministic and free

No model call. Which agents run, whether the risk engine applies, whether verification applies, and what the investigation is scoped to are all settled by the classification. The plan is recorded before execution, so a report can distinguish "security was investigated and found nothing" from "security was never investigated" — a distinction that is unrecoverable after the fact.

Design principle — stubs refuse, they never reassure

An unimplemented security agent returning "no incidents found" would be the most dangerous line in the repository: indistinguishable downstream from a real negative finding, and strictly more confident than the evidence permits.

Every stub contributes zero claims plus a recorded limitation. The security stub says outright that its silence means nothing was searched, not that nothing exists. What made this easy is that A1 and A2 had already built the vocabulary for it — unknown is not normal, unsupported claims score zero, and a report with no verified findings refuses to conclude.

Two constraints discovered by testing

  • State carries plain dicts, never models. Checked empirically rather than assumed: under strict serialization a model in a state channel is blocked, and without it, it silently rehydrates as a plain dict. A node reading evidence[0].summary would work on the turn that wrote it and crash on the next.
  • The shared-channel reducer takes a reset. Parallel agents writing shared channels need a reducer, but plain append also accumulates across turns — investigation #2 would inherit #1's evidence and report claims it never gathered. Same bug class as the sticky escalation flag found in B1.

The report reproduces the spec's key distinction

FindingConfidenceVerification
Liquidity outflows were abnormally high over the last 24 hours0.88Verified
The abnormal outflows were caused by a security exploit0.14Insufficient evidence

The system can detect that something abnormal happened without claiming to know why — with the contradicting evidence surfaced in its own section rather than buried.

Agents

C1

Research Agent

Shipped

The first stub replaced by a working agent. It reuses hybrid_search unchanged — the ordinary path and the investigation path share the same measured retrieval, because maintaining two retrievers and measuring one is how quality quietly diverges.

question → decompose (4 angles) → retrieve each → evidence → synthesize (claims cite excerpt numbers) → link → verified claims 1 model call local, free deterministic 1 model call deterministic

Two model calls total regardless of how many sub-queries run, because retrieval is local and free. That is the whole reason decomposition is affordable here.

The load-bearing part The model proposes claims and cites excerpts by number; code resolves those numbers against the evidence actually retrieved. Out-of-range citations are dropped, repeats are linked once, and a claim left with no valid citation is discarded — not kept at confidence zero. It would score zero anyway, but a zero-confidence claim still sits in the record inviting someone to read it as a weak finding. It is not a weak finding; nothing supports it.

Measured on the real corpus

Three angles versus one query, k=5, protocol-filtered:

ProtocolChunks (1 → 3 angles)Distinct pagesGain
ethena5 → 155 → 133.0×
hyperevm5 → 153 → 93.0×
hyperliquid5 → 152 → 43.0×

Three times the evidence surface with zero chunk overlap between angles. The 2 → 4 row is the interesting one: Hyperliquid's funding docs are concentrated, so decomposition deepens — more chunks from few pages. Ethena's are spread out, so it broadens. The effect depends on corpus structure, not just query count.

Honest caveat More evidence is not automatically better. Nothing yet checks whether the extra chunks are useful, and they are more work for verification to get through. That needs a golden-set measurement that has not been done.

Three defects found wiring it up

  • Default arguments made the agent unpatchable. A default binds the function object at import, so swapping the module attribute still reached the network — the full suite hung on its first run after the stub was replaced.
  • Verification computed verdicts but never applied them. The report read each claim's status, which stayed unverified, so a well-evidenced investigation rendered as "produced no findings".
  • The breadcrumb stuttered on real data — "How USDe Works › How USDe Works › How USDe Maintains its Peg" — visible only against the real corpus, never against fixtures.
C2

Blockchain Agent & feature store

Shipped

The risk engine now has data. A SQLite feature store — standard library, no new dependency — persists readings over time, and a scheduled collector keeps them current. Anomaly detection is a comparison against a baseline, and until this existed there was no baseline to compare against.

The agent gathers; it does not judge

It produces evidence — measurements with times and sources — and no claims. Claims about abnormality are emitted by the risk engine from the arithmetic, linked to the readings they were computed from. So every claim that something is unusual traces to a computation someone can redo by hand, rather than to an agent's impression of a number. A signal that cannot be tied back to a stored reading is dropped, not asserted — the same rule the Research Agent's citations get, with no exemption for the risk engine.

Two rules the storage layer enforces by shape

  • Writes are idempotent. Collection is scheduled, schedules overlap and retry, and a duplicated reading is not harmless — it doubles that value's weight in the baseline it later forms part of. A conflicting later value never overwrites a recorded one either: that is a source inconsistency, and rewriting history to match the newest answer erases the evidence of it.
  • The baseline query cannot include the point being tested. Rather than documenting the risk engine's core rule and hoping, the function callers reach for takes the current timestamp as an exclusive bound.
Key finding — and I had the reason backwards

Cumulative counters (total transactions, total addresses) must be differenced into rates before scoring. I first justified this as "a counter would flag critical every day". That is wrong. Measured on 30 days of ~1000 tx/day:

Next dayRaw counterAs a rate
normal (+1000)z=+1.76 normalz=−0.12 normal
3× surge (+3000)z=+1.98 normalz=+34.6 critical
10× surge (+10000)z=+2.77 elevatedz=+156 critical
chain stalls (+5)z=+1.64 normalz=−17.4 critical

A counter sits at its all-time high by construction, so its score is pinned around +1.7 whatever happens — just under the elevated line. It is not noisy; it is blind. Look at the last row: a chain that stops entirely reads normal, because the counter is still near its peak, it simply stopped climbing. A catastrophic outcome dressed as an all-clear — which is worse than a false alarm, and precisely what this system exists to prevent.

Verified against live endpoints

ProtocolResultBehaviour
hyperliquidCollecting8 live series accumulating — mark price, funding, open interest, 24h volume, across ETH and BTC
ethenaNo sourceRefuses correctly: "no on-chain data source is wired up — the absence of an anomaly here means nothing was measured"

Needs your decision — HyperEVM's explorer is gone

hyperscan.com/api/v2/stats now returns 404, along with every other endpoint tried: the bare domain, /api/v2/blocks, /main-page/blocks, the Etherscan-compatible /api surface, and the Blockscout-hosted alternative. The public API has moved or been withdrawn since it was last verified.

This is pre-existing and not caused by this step. It also breaks the shipped live-data path — a user asking "what is the latest HyperEVM block" gets an error today. Both paths degrade honestly, with no fabricated numbers and no false all-clear, which is verified. But HyperEVM on-chain data is dead until a working endpoint is found.

Three options: find the relocated Hyperscan API, swap to a different explorer, or drop HyperEVM's live tool and let it answer from documentation only.

What it honestly reports today A feature store that started collecting today has almost no history, so nothing can be scored yet — each series reports how many more readings it needs before a baseline exists. That is the correct output, not a placeholder: a version that produced findings from one reading would be lying.

Two defects found

  • I reintroduced C1's default-argument bug. Same mistake, one step later — a default binds at import, so the injected collector was ignored and the offline test reached a live explorer.
  • Evidence records could not state their own identity. The ids were plain properties, so they vanished when a record was serialized into graph state — leaving links unresolvable without rebuilding the model. They are computed fields now, which the evidence graph will need.
C3

Security Agent

Shipped

All three specialists are real now. This one searches two sources that are deliberately never blended: a curated registry of security findings, and the protocol's own security documentation — audits, custody arrangements, bug bounties, risk disclosures — which is already in the corpus and costs one local retrieval.

The four categories, and the rule that keeps them apart

CategoryMeaningMay support a finding?
Confirmed incidentIt happened, and a named source stands behind thatYes
Known vulnerabilityA weakness is documented, used or notYes
Suspicious signalSomething looks off; nobody has established whatContext only
Unverified claimSomebody said soContext only

Unestablished findings attach as neutral. They appear in the record so a report can show them, and they can never raise a confidence score. That is the spec's own worked example turned into a rule: a forum post attributing an outflow to an exploit does not make the exploit likelier — it makes the rumour visible. A test adds four rumours beside a confirmed incident and asserts the score does not move.

Classification and source reliability are independent axes. A confirmed incident reported by a community researcher is confirmed and community-tier. Collapsing "who said it" into "how established is it" is the specific mistake the separation exists to prevent.

The registry ships empty, on purpose

An entry labelled confirmed incident is trusted by everything downstream — it can support a claim, raise a confidence score, and appear in a report as established fact about a named protocol. Populating it from my recollection of DeFi history would put defamatory content about real protocols behind that label. Every entry needs a citation an operator has actually read.

So the agent reports: "no security findings are on file … this means nothing has been recorded — NOT that nothing has happened. No external threat-intelligence feed is connected." Adding entries is an operator decision, documented in the file itself.

The documentation stream needed equal care A risk-disclosure page is a protocol describing a risk it designed around. It is not evidence that anything went wrong. Treating "Ethena documents custodial risk" as a security finding would make every well-documented protocol a suspect and every undocumented one look clean — precisely inverted. So documented risks produce a claim about what is documented, which says so explicitly, and never a claim that a vulnerability exists.

Two defects, both introduced here

Parallel agents raced to build the vector store

With two agents retrieving instead of one, the parallel fan-out finally exercised something that had been latent: memoisation caches a result, it does not make computing that result atomic. Two threads missed the cache together, both started building a database client, and the second died — taking the whole investigation with it.

Fixed with a lock taken before the cache lookup. Guarding the body instead would only serialise two concurrent misses; both would still construct, and the construction is where the race lives.

The report led with confidence on a partial investigation

Asked "is Ethena showing any significant risk?", the summary opened with "high confidence (0.98)". True of the finding it described — a claim about what the documentation covers — but the risk engine had measured nothing and the incident registry was empty. A reader skimming the first line would take that as an answer about risk.

This is the same failure the whole system is built against, one level up. Coverage now comes first: unmet stages are derived from the plan — which is why the plan is recorded before execution — and the summary opens "Partial investigation. … not an answer about the parts that were not."

C4

Verification Agent

Shipped

The agent layer is complete. This is the one whose success looks like removing output: it finds nothing, it only asks whether what the other agents found holds up.

Six checks, five of them free

CheckQuestionOn failure
supportDoes any evidence point at this?Blocking
contradictionIs it outweighed by evidence against?Blocking
source qualityIs anything behind it better than unverified?Weakens
temporal relevanceIs the evidence still current enough?Weakens
numeric consistencyDoes every figure stated appear in the evidence?Weakens
overclaimingDoes it assert more than its evidence carries?Weakens
entailment (optional)Does the evidence actually bear on this claim?Blocking
The two that nothing upstream can do

Numeric consistency. If a claim states a figure, that figure must appear in the evidence behind it — magnitude-normalised, so "$12.5M" and "12,500,000" compare equal, with tolerance for rounding. This is the cheapest defence against the most expensive error a DeFi answer can make: a confidently stated number nobody measured. Retrieval cannot catch it and grading cannot — the chunk is relevant, the sentence is fluent, and the number is invented.

Overclaiming. Causal language ("caused by", "due to", "resulted in") and absolutes ("never", "guaranteed", "proves") raise the number of independent sources required. Causation is a larger assertion than observation, and a system that scores them identically will publish the second dressed as the first. This is the spec's own worked example turned into a rule.

Demonstrated on a deliberately bad synthesizer

ClaimVerdictConf.Reason
"maintains its peg through arbitrage"Verified0.88—
"holds exactly $87,300,000 in reserves"Partial0.62that figure appears nowhere in the evidence
"the peg is guaranteed because of the hedge"Partial0.62causal claim resting on one source
Entailment is off by default, and that is disclosed The one model call — "does this evidence actually bear on this claim?" — costs one request per claim that survived the free checks. It is the right thing to pay for on an investigation someone will act on, and the wrong thing to pay on every turn. When it is off the report says so: evidence was verified as present, sourced, current and numerically consistent, but not as actually being about the claim it supports. The cost of skipping is stated, not hidden.

Two defects

My own status logic conflated the two failures it exists to separate A claim with no evidence at all produced an agreement score of 0/0 → 0.0, which tripped the contradiction check — so "we could not establish this" was reported as "we have reason to believe otherwise". Precisely the merge the four statuses exist to prevent, in the component built to prevent it. Nothing arguing against a claim cannot be a contradiction; the support check is what should block it, with the right reason.

The second was a genuine gap the new checks exposed: risk-engine claims quote a baseline median and a z-score, which are derived from history that lives in no evidence node. Numeric consistency flagged them, correctly. The computation itself is now recorded as evidence — a statistical-signal node, a kind defined back in A1 and unused until something needed it.

D1

Evidence Graph

Shipped

The flat record already holds every claim and every citation, so the graph had to earn its place. It does, in two ways a list structurally cannot.

1 — It answers "why did you conclude that?" by walking

WHY DID YOU CONCLUDE THAT? → USDe maintains its peg through arbitrage. [supported_by] evidence: Peg Arbitrage Mechanism [supported_by] evidence: Peg Arbitrage Mechanism › Agent Instructions [from_source] source: Peg Arbitrage Mechanism

Rebuilt from a checkpoint, so the question stays answerable after the fact without re-running anything. Only provenance edges are followed — the relationships leading sideways to a protocol or an agent are real, but following them would answer who said it rather than what it rests on.

2 — It reveals when findings are not independent

The reason it exists

Two claims each carrying citations look like two corroborated findings. Several pieces of evidence converge on one source node, and suddenly they are one finding stated twice. Measured on a live run:

2 claims · 5 pieces of evidence · 5 distinct sources → 1 independent line of evidence

The report's new Provenance section says so plainly: "2 claims share the source 'How USDe Works' — they corroborate each other only as far as that one source is correct." That bounds what the findings are entitled to claim, and nothing else in the system can see it.

Choices

  • No graph library. Tens to low hundreds of nodes and a handful of specific traversals — adjacency dictionaries are the whole implementation.
  • Built per investigation, from the record. A lens over state, not a second store that can drift out of agreement with the first — which is precisely the failure A0 was about. Persisting it across investigations is a later and different problem.
  • The node vocabulary is shorter than the spec's. A node type nothing constructs is a promise the graph cannot keep, and an empty category in a provenance view reads as "we checked and found none".
  • Rendered as a diagram in the report, as text rather than an image — it costs nothing and diffs cleanly.

No defects in this step.

D2

Report refinements

Shipped

The structure shipped in B2 and provenance in D1. This is the difference between a report that contains the right headings and one a reader can actually rely on. Five gaps, none of them new sections for their own sake.

The summary and the assessment were the same paragraph

Word for word. §15 gives them separate headings because they do separate jobs, and printing one twice wasted the other. The summary now says what was found, coverage first. The final assessment says what the investigation is entitled to conclude — a narrower statement that has to name what stays open:

Final assessment, on a real run "The strongest finding is well supported and can be relied on as stated (confidence 0.88). This conclusion is bounded by what was searched: no on-chain metric could be scored against a baseline and no security findings were on file to review. Nothing here speaks to those."

Security findings had nowhere to appear

§15 lists the section and it was missing, so §10's four categories had no place to be shown apart. Established findings and unestablished ones now render under separate headings, with the second group stating outright that nothing under it supports a conclusion. A rumour printed beside a confirmed incident, in the same typeface, is read as a second incident — which is exactly the merge that separation exists to prevent.

A subtlety the freshness stamp exposed

An artifact about on-chain data with no as-of window is dangerous: the numbers look current because the document is. But adding one naively dated a year-old documentation page to today — a document has no authored date the system can see, so its timestamp is a fact about the crawl, not the content.

The two are now reported separately: "Measurements are as of 2026-08-20. 12 documentation excerpt(s) were retrieved on 2026-08-20; the documentation's own age is not known to this system."

The report is now data as well as prose

§15 calls the output a structured intelligence artifact, and markdown alone is half of that — it can be read, but not queried, diffed by field, or scored. Alongside the prose there is now a structured form carrying findings with their confidence, band and limiting factor; security counts per category; provenance including how many independent lines of evidence the claims rest on; the evidence window; and what was not covered. Both are rendered from the same record, so a reader and a script cannot be told different things — there is a test for exactly that.

Evidence lists per finding are also capped now: a finding backed by twelve sections was burying the next one under twelve bullets.

D3

Evaluation

Shipped

The last phase. Three new harnesses, all free to run: verification, anomaly detection beyond a single threshold, and agent selection. The offline suite goes from two harnesses to five, so a routine run now covers the investigation path too.

Verification — scoring the stage that exists to reject things

Eighteen labelled cases, one per way a claim can be wrong: unsupported, fabricated figure, causal overreach, absolute overreach, outweighed by contradiction, anonymous source, stale evidence, and combinations. Alongside them, cases that must be accepted — a set of only-bad claims would score perfectly against a verifier that rejects everything.

MetricValueReading
claim accuracy1.000exact status agreement
false verification rate0.000bad claims accepted — the asymmetric one
unsupported-claim catch rate1.000—
contradiction detection1.000—
over-rejection rate0.000good claims wrongly rejected — the cost side
What this number is and is not The cases are constructed, one per failure mode, written by me against a system written by me. That makes this a regression guard, not an estimate of real-world rates — real traffic will have a different mix and needs its own labels. The case file says so, and so should anyone quoting the figure.
My first anomaly benchmark measured nothing

It drew anomalies from 6–15 against a baseline of 2.3 ± 0.25 — about fifteen standard deviations of separation. Every metric read 1.000, including ROC-AUC. A benchmark whose ceiling is reached by any working implementation cannot distinguish a good detector from an adequate one.

Rebuilt with three tiers that actually degrade:

TierPrecisionRecallF1ROC-AUC
easy (~15σ)1.0001.0001.0001.000
moderate1.0000.8890.9410.998
hard (inside the tail)1.0000.3890.5600.978

The shape is the finding. Precision and false-positive rate hold at 1.000 and 0.000 across every tier while recall collapses from 1.00 to 0.39: the 3σ bar never cries wolf, it misses subtle shifts. And ROC-AUC stays at 0.978 while F1 falls to 0.560 — which locates the loss in the threshold rather than the score. Lowering the bar would recover recall if subtle shifts ever mattered more than quiet. That is precisely what a threshold-independent metric is for, and why the spec asks for one.

A rate over an empty denominator is undefined, not zero

The harness divided by zero on a case set where everything was expected to verify. The fix is not a guard returning 0.000 — that would report "no bad claims accepted" for a measurement that never ran, which is the most reassuring possible reading of nothing having happened. It reports n/a, on the same principle that keeps "unknown" apart from "normal" everywhere else in the system.

After the roadmap

The thirteen phases closed with four operational items open. Three of these entries clear the first of them; the fourth arrived as a review of the work itself.

E1

Chain reads over JSON-RPC

Shipped

What actually happened to the explorer

The site was reported as working — and it is. It had been rebuilt as a web application, and its API went with the rebuild. Every surface the tool used is gone: the Blockscout v2 routes 404, and the Etherscan-compatible one returns HTTP 200 carrying an HTML page.

The trap that nearly caught this A status-code check would have called that 200 a success, and a lenient parser would have turned the HTML into an empty result — which downstream is indistinguishable from "the chain reported nothing unusual". This project's own notes already recorded the same trap for a documentation site that served an SPA fallback to llms.txt. It is now a rule at the client boundary: validate the shape, never the status code, and record not collected rather than a zero.

Why RPC, and why it is the stronger choice

An explorer's API is a product feature; it gets redesigned when the website does, exactly as happened. JSON-RPC is a protocol standard. But the decisive argument is not fragility — it is provenance. Source reliability here is assigned by rule from a whitelist treated as a security boundary, and an endpoint inferred from a minified JavaScript bundle has nowhere to sit in that model. It cannot be tiered, so it cannot be scored, so a claim resting on it cannot be cited. It fails at the schema, not at runtime.

The client is therefore provider-agnostic: hosts live in a registry, and every call returns the value and the provider that served it, carrying its tier. When a weaker provider answers, evidence built from it scores lower automatically.

Three measurements that changed the design

MeasuredValueConsequence
Block time0.99 s—
Gas limits3,000,000 and 30,000,000Docs cited 2M; the split threshold sits between either way
Big blocks per 901A fixed 30-block window would never sample one

The last row was caught empirically, not reasoned about: the first collector ran cleanly and silently produced no big-block readings at all. The scan now walks back from the head and stops once it has enough of both, costing about 63 calls against a 100-per-minute limit.

The dual-block split is not cosmetic. Sampled together, transactions per block is a mixture of two populations, and its variance is dominated by which kind of block was sampled rather than by chain activity. The severity thresholds were calibrated on unimodal data, and the robust score handles skew and contamination but does nothing about bimodality — the series would carry large stable variance and simply never fire.

Block height, as a counter, on purpose

The cumulative counters lost with the explorer are not missed — a counter sits at its all-time high by construction, so a chain that stops entirely still reads normal on one. But block height is registered as a counter deliberately: differenced, its rate is blocks produced per interval, which is chain liveness. It is the one thing a counter measures better than a gauge could.

The live-data path, and what it now declines to say

Network overview, balances and contract-vs-account detection all work again, with block time straight from timestamps. Two capabilities went with the explorer's index, and both refuse explicitly rather than degrading:

"I'm not saying no contract matches 'WHYPE'. I'm saying I have no way to search for one." An empty search result is indistinguishable from a search that found nothing — for someone hunting a token contract, that is the difference between "try again with an address" and "that token does not exist". Verification status reports absent rather than false, for the same reason.

A foot-gun, closed Testing the collector meant writing to the live feature store, and off-schedule readings sit seconds apart in a series meant to be evenly spaced — which shrinks the baseline they join and suppresses the anomalies it exists to catch. Two such runs had to be deleted by hand. --dry-run now exercises the full path, network calls included, up to the point of writing.
E2

Chain-state tier, and claim-kind weighting

Shipped

A single ranking over sources cannot be right, because the ordering genuinely inverts between the two most authoritative sources this system has.

The argument

Documentation records what a protocol commits to. Chain state records what it is doing.

"Reserves are $87.3M" is settled by the chain — documentation describes intent, and intent can be stale or aspirational. "Liquidation uses a three-minute TWAP" is settled by the documentation — you cannot read a rule off a sequence of transactions, because observed behaviour is consistent with many rules. Neither strictly outranks the other, so reliability became a matrix.

Claim kindChainDocsSettled by
state1.000.55chain
mechanism0.651.00documentation
event0.950.65chain
unspecified0.900.90—

Undeclared tops out below 1.00 in every column: a claim whose kind nobody stated has not earned the top of any of them, which also makes declaring an improvement rather than a free win.

Two corrections, both caught in review before the registry work

Kind was agent identity wearing a costume

Every claim's kind was hardcoded per agent — research always mechanism, security always event, risk engine always state. That is agent identity re-entering the weighting immediately after being deliberately kept out of claim identity, and it is wrong in a predictable direction: a documentation page stating "reserves are $87.3M" would be scored as a mechanism claim, giving documentation 1.00 in the one row where it should be 0.55.

Kind is now declared per claim, bounded by a table of what each agent is competent to assert. Research may say a page describes a mechanism or states a value; it may not say an incident occurred. That bound is what stops the declaration being a free parameter — the thing being scored does not get to pick its own row.

The compensatory failure, relocated into the matrix

Reliability was already a maximum within tier, so that half was safe. But evidence quality was additive, and it is a separate factor in the same geometric mean. Measured on a mechanism claim:

SupportQualityReliabilityScore
1 documentation page0.6001.000.880
20 chain observations0.9680.650.891 ←
100 chain observations0.9930.650.896 ←

The low weight capped one axis while quality accumulated around it — the same shape as the confidence bug from A1, one layer up. And the reason dictates the fix: underdetermination does not improve with observation count. A hundred liquidations are consistent with the same dozen rules as ten.

So sources that are the wrong instrument for a claim's kind are now capped, not discounted: however many there are, they contribute at most one source's worth of corroboration between them. Quality is now flat across 5, 20 and 100. It is not special-casing the chain either — ten documentation pages stating a value produce identical quality to one, on a claim about state.

E3

Contract registry

Shipped

The tier and the scoring were ready; nothing produced chain-tier evidence for a claim about state. That needed contract addresses — a whitelist decision, with the same discipline as the protocol whitelist and the incident registry.

Why contract addresses are admissible where an API endpoint was not

This registry can check itself. An undocumented endpoint has to be taken on faith; a contract can be asked what it is. Identity is confirmed against the chain before any reading is kept, so a mistyped address, a redeployment, or a proxy pointed elsewhere stops collection loudly rather than producing plausible numbers about something else — at the highest reliability tier, which is where a wrong number does most damage. A decimals mismatch even names the size of the error: "every scaled reading would be wrong by a factor of 1,000,000,000,000."

One entry, found by asking the chain

An address encountered while testing self-identified as Wrapped HYPE (WHYPE), 18 decimals, and its native balance tracked its total supply — the invariant a wrapper should satisfy. That cross-check is what made it a registry entry rather than a guess.

MetricMeasuredWhat it is
token_total_supply5,404,422.32circulating supply
wrapper_native_backing5,404,422.32native coin locked
wrapper_backing_ratio1.000000the invariant

The third is the reason this was worth doing. It is not a statistic about activity, it is an invariant: a wrapper should hold exactly one native coin per wrapped token, so the series should sit at 1.0 and any sustained departure is under- or over-collateralisation. That is a finding, and the anomaly detector already knows how to spot a departure from a stable baseline.

The guard that rejected everything it was protecting

The ratio must be computed from reads at one block: the public endpoint serves calls at the head only, blocks arrive about every second, and a wrap settling between two sequential reads would move one number and not the other. Reading 1.0002 because the chain advanced mid-measurement is indistinguishable, in the store, from 1.0002 because the wrapper is over-collateralised.

So the reads were bracketed with the block height — and the guard fired every single time, because the client's own throttle makes four sequential calls span two or three blocks by construction. The guard was right; the reads were wrong. They are now a single batched round trip, matched by id rather than position so a shuffled response cannot silently swap two values.

The loop closes

WHYPE total supply is 5,404,422.32 tokens, fully backed at a ratio of 1.0000. verdict verified reliability 1.00 (chain tier, state claim) confidence 0.88 [high] checks support, contradiction, source_quality, temporal_relevance, numeric_consistency, overclaiming

Numeric consistency passes because the figures came from the reading itself. Contract state also got its own evidence kind with a 4-hour half-life — a reserve balance under the day-scale decay would sit at 0.71 currency half a day later, a 1.00-reliability source vouching for a moment well past.

Corrections & retractions

Repairing the index invalidated measurements the README presented as established. Both affected claims have been corrected in place, with the reasoning recorded rather than quietly overwritten.

Retracted

"The protocol filter is not merely hygiene — it is worth +0.031 recall on its own."

On a clean index the filter buys +0.000 recall, and leakage without it is 6%, not 35%. The orphans were overwhelmingly untagged, so the metadata filter excluded them from every filtered run while the unfiltered run retrieved them freely. The ablation was never comparing filtered against unfiltered search over one corpus — it was comparing a clean corpus against a junk-laden one and crediting the difference to the filter.

This also re-explains a trend the README had recorded honestly and interpreted wrongly. The filter's measured benefit shrank as protocols were added (+0.036 at two, +0.031 at three), attributed at the time to "adding a protocol spreads the competition". The likelier explanation is arithmetic: the orphan count was roughly fixed while the live corpus grew from 673 to 1,091, so the junk fraction fell and the artifact shrank with it. It has now reached +0.000, which is where that line was always heading.

The filter still earns its place — for a different reason It provides a guarantee, not a lift: 0 of 131 cases pull a wrong-protocol chunk, versus 25 without it. recall@k structurally cannot see that difference — it only asks whether the right page is in the top-k, not whether a rival protocol's page is sitting next to it. That adjacency is exactly what produces a confidently wrong-protocol answer. The value is context precision.
Strengthened The cross-encoder is doing considerably more than it was credited with: MRR gain +0.047 → +0.091, recall gain +0.008 → +0.023. Fusion's own MRR fell on the clean index, because the orphans were duplicate copies of correct pages padding its top ranks for free. The old "ranking, not recall" framing came from a recall gain that sat flat at ~+0.008 across both drifted runs — that flatness was the contamination.

The general lesson, now written into the README: a same-run ablation is only as trustworthy as the index underneath it. Both ablations were internally consistent — one process, one corpus, one question set — and one of them still measured an artifact for months. The response was not "measure more carefully" but "assert the invariant".

Vocabulary

These terms have exact meanings in the code, and several distinctions that look pedantic are load-bearing.

Evidence
One observation, from one source, at one time. Identified by a hash of its content, so the same fact found twice is one node.
Claim
An assertion an agent is prepared to be held to. Carries no confidence of its own — confidence is computed from its evidence, so nothing can score itself.
Stance
How a piece of evidence relates to one specific claim: supports, contradicts, or neutral. A property of the relationship, never of the evidence.
Source tier
Primary (the chain, or a protocol's own whitelisted docs) → official → community → unverified. Assigned by rule, never by a model.
Verified
Evidence was found and it holds up. Distinct from insufficient evidence (we do not know) and contradicted (we have reason to think otherwise).
Unknown vs normal
A severity of unknown means a metric could not be assessed. It is never reported as normal — a blind spot must not read as a clean bill of health.
Notable vs anomaly
Notable (≥2σ) earns a row in the statistics table. Anomaly (≥3σ) earns a paragraph. Conflating them is how a detector gets muted.
Query type
How much machinery a question needs. A separate axis from intent, which decides whether the agent may act at all — and intent always wins.
